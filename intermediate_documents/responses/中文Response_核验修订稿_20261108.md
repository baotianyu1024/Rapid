## Meta Revision 1：补充外部基线、数据集与模型比较

### 1）基线选择

感谢审稿人指出比较不充分。我们将保留 HugeCTR，并补充 TorchRec 自动分片、EMBark、HET-GMP、Herald 和 BagPipe，覆盖自动分片、联合 embedding/sample 放置以及缓存预取与输入调度。我们已执行规划、通信统计和单机 8 卡短训；当前训练窗口吞吐不能替代含预处理的完整训练时间。

### 2）数据集与模型

本轮端到端真实数据包括 Criteo Kaggle、Criteo Terabyte 和 Taobao，各测试 DLRM、DLRM-DCNv2、Wide&Deep、DeepFM，共 12 个数据集／模型组合。MovieLens-25M 已按实验范围调整退出本轮矩阵；此前的 MovieLens 测量仅作历史记录，不填入当前正式表。两个 Criteo 数据集仍归为同一应用领域。

模型选择参考了 BagPipe 对 DLRM、Wide&Deep、Deep&Cross 和 DeepFM 的比较，以及 EMBark 的 DLRM-DCNv2 实验。[BagPipe](https://arxiv.org/pdf/2202.12429)、[EMBark](https://developer.nvidia.com/blog/boost-large-scale-recommendation-system-training-embedding-using-embark/)。当前复测固定主 embedding dim=32、每卡 batch=8,192；T 系列因官方单分片仅有 65,536 行，按其原配置每卡 batch=512 单列。正式比较仍需共享数据划分、网络结构、初始化和有效 batch。本轮本地 Criteo 实验使用固定 multi-hot 扩展，各方法共享同一映射；原始单 hot 版本的训练对照另列，不将扩展后的共现直接归为原始单 hot 数据的性质。当前完成度见[审计报告](中文Response完成度审计_20261103.md)。

另加入 HugeCTR 官方 T180、T200、T510 负载，直接执行官方数据生成器，保留逐表词表大小、hotness、ID 随机置换及 Zipf(1.1) 采样。固定代码版本 `61b4d539aa7044e9021896f0485be1a6697f4f44`；T180 仅修复输出文件变量名笔误。模型维度取同版本 benchmark 配置：T180 为 32/64/128/256，T200 为 64/128，T510 为 128。官方 T180 名称对应的脚本实际展开为 177 张表，我们保持原配置，不自行补表。这些合成数据仅用于通信与性能测试，不用于精度验证。[官方生成器与运行说明](https://github.com/NVIDIA-Merlin/HugeCTR/tree/61b4d539aa7044e9021896f0485be1a6697f4f44/benchmarks/embedding_collection)。

已重新生成并校验这三种负载的官方第 0 分片；hash owner 通信、静态 ACP 及完整词表显存下界见[官方 T 系列生成与通信诊断](官方T系列生成与通信诊断_20261103.md)。本轮已追加多方法通信回放与单分片活跃工作集 GPU 训练，具体口径和原始证据见[扩展基线与 T 系列实测](扩展基线与T系列实测_20261104.md)。

BagPipe 的 12 个真实数据组合均采用修正后的 int32 标签、多热 once-ID 解析和与 TorchRec 一致的参考网络形状，使用原生 oracle、embedding server 与 8 trainer，AdaGrad 0.01、每卡 batch 8192、dim32、lookahead 8。Taobao 每卡缓存 100 万行，Kaggle、Terabyte 每卡缓存 1600 万行。训练前仅解析一次已打乱的 15 个全局 batch，训练阶段从内存重复，510 步吞吐取 8 个 rank 中最长训练循环墙钟；逐 rank 日志和汇总见[BagPipe CSV](bagpipe_d32_e2e_results_20261105.csv)。Kaggle／DLRM 的训练窗口约 455 秒，其中各 rank 的平均缓存同步关键路径约 0.77 秒/步；输入文件读取已经移出训练窗口，但原生 oracle 调度和缓存同步仍在计时中。

Herald 的 12 个真实数据组合均完成 8 卡、510 步，使用 LAIA 调度器、Hetu GPU executor、AdaGrad 0.01 与相同参考模型；输入在训练前装入内存，训练窗口包含在线分配和参数服务器通信，逐 rank 记录见[Herald CSV](herald_d32_e2e_results_20261105.csv)。Kaggle 和 Terabyte 吞吐约 9,845–10,663 samples/s，远低于 Taobao 的 415,450–441,185；多热 LAIA 在线样本分配是主要瓶颈，不能把这组结果解释为 GPU 算子本身慢。已修复旧 BCE 的数值溢出，并将通信计划与缓存去重改为等价批量构建。Taobao 四项已用最终代码重测。

Kaggle／DeepFM 的 BagPipe 510 步 loss 从初始约 328 降至各 rank 约 39.5–42.6；Terabyte／DeepFM 的末步 loss 约 12.0–16.3。两者仍明显偏高；表内吞吐仅表示系统完成了训练窗口，不能据此声称与其他框架达到相近精度。

已完成的真实 8 卡 GPU 子集实测及逐轮日志见[Response R1/R5 真实 GPU 续测报告](Response_R1_R5真实GPU续测_20261102.md)：Criteo Kaggle 和 Terabyte 的 DCNv2 风格模型在 128 维、每卡 batch 2,048 下完成 HugeCTR、TorchRec、HET-GMP 与 RAPID 三轮对照；Kaggle 在每卡 batch 8,192 下另有 RAPID 与 TorchRec 对照，Taobao/DeepFM 也有三框架对照。**计时口径纠错：**旧报告 HugeCTR/RAPID 的 `Time(10 iters)` 漏计了打印块间的时间，不能与 TorchRec 的完整 step 墙钟直接排名；按日志墙钟复核，Terabyte 2,048 batch 的 RAPID 为 298,502、TorchRec 为 329,287 samples/s，旧文“RAPID 快 0.24%”撤回。进一步导出 TorchRec 实际计划并过滤本卡 NCCL 调用后，RAPID 与 TorchRec 默认计划的远端发送分别约 26.56 和 26.69 MB/卡/步；两者表策略与协议不同，详见[吞吐与通信复核](TorchRec_HugeCTR吞吐与通信复核_20261103.md)。此前的[计时排查](多日吞吐排序与计时口径排查_20261103.md)保留旧日志纠错记录。上述 dim128、每卡 2,048 的数字不能与表 R1 的 dim32、每卡 8,192 数字合并；R1 未适配的框架仍明确标注原因。

按相同多日 Criteo 分片子集将本地 batch 提高到 8,192 后，[显存与吞吐复测](本地Batch8192显存与吞吐复测_20261103.md)中 TorchRec 两轮均完成 510 步，完整训练循环吞吐为 **507,444 / 506,945 samples/s**，GPU 峰值已分配显存约 4.74 GiB/卡；其 planner 重选为 18 DP、7 table-wise、1 row-wise。原生 HugeCTR 的 26 MP 默认缓冲在 `model.compile()` OOM；根据本数据全 16 批的单卡键数上界，把上游 `DENSE_UNIQUE_RATIO` 与 `WGRAD_UNIQUE_RATIO` 均设为 0.25 后，26 表全 Unique 完成 510 步，完整 `fit` 墙钟吞吐 **321,611 samples/s**。HugeCTR 只把表 20 改为 Reduction、其余 25 表仍为 Unique 时，默认缓冲也能完成 510 步，吞吐 **409,027 samples/s**。前 30 步每卡每步远端 send payload：HugeCTR 全 Unique **487.79 MB**、表 20 Reduction **289.98 MB**、TorchRec **61.56 MB**；AllReduce 输入分别为 **64.18 / 64.18 / 107.93 MB**。这些是 NCCL API 逻辑字节，不是实际链路流量。同 batch 的 Nsight 时间线显示 HugeCTR 全 Unique / 表 20 Reduction / TorchRec 的每步 NCCL kernel 时间分别为 **124.43 / 86.18 / 75.14 ms**，前两者的通信计算重叠为 **0 ms**，TorchRec 为 **22.86 ms**；吞吐仍以上述无 profiler 的完整训练循环为准。此前“Kaggle 上 TorchRec 较慢”比较的是 RAPID+HugeCTR，且早期 HugeCTR 内部块计时曾与 TorchRec 墙钟混用；纠正后 Kaggle 8,192 的 RAPID 与 TorchRec 接近，不能与本轮原生 HugeCTR 直接类比。TorchRec 在本轮已测配置下更快，但各配置表策略与通信协议不同，不能概括为框架本质快慢；HugeCTR 的单表 Reduction 也不是重新规划的完整 ACP。RAPID 旧 2,048 计划的物化输入在 8,192 OOM（仅容量探测），须重新规划才有有效的该 batch RAPID 对照。

### 2）为什么在所述条件下保持模型计算

设第 $t$ 次更新的原始 global batch 为 $\mathcal{B}_t$，含 $N$ 条样本。原目标函数为

$$
L_t(\theta,E)=\frac{1}{N}\sum_{i\in\mathcal{B}_t}\ell(f_{\theta,E}(x_i),y_i).
$$

RAPID 只将该集合重新划分为各 rank 的 $\mathcal{B}_{t,r}$，且保持不相交并集及样本重复次数不变，因此

$$
\frac{1}{N}\sum_r\sum_{i\in\mathcal{B}_{t,r}}\ell_i=L_t.
$$

$$
\sum_r\frac{1}{N}\sum_{i\in\mathcal{B}_{t,r}}\nabla\ell_i=\nabla L_t.
$$


embedding 放置相当于对物理行做一个置换 $P$。只要 lookup 使用同一逻辑 ID，初始权重和 optimizer state 同步置换，取回的向量值不变；对逐行 SGD/Adam，正确聚合后的更新满足

$$
U(PE,Pg,PS)=P\,U(E,g,S).
$$

Unique 只去除重复传输，不删除模型所需的重复出现；恢复和 pooling 保留原 multiplicity，反向仍对同一逻辑 ID 汇总全部梯度。Reduction 的分段求和在精确算术下与原求和相同。因此，从相同逻辑初始参数出发，可逐步归纳得到相同的损失、梯度和更新后模型。

该结论要求相同 loss 归一化、完整 global batch 梯度汇总后执行一次 optimizer 更新、相同的 optimizer state，以及不依赖 rank 的随机操作和归一化。物理行重排后仅复用随机种子并不足够，必须按逻辑 ID 对齐初始权重。rank-local BatchNorm、不同的 dropout 随机掩码或不同稀疏更新次数不满足上述条件。

AUC 由正负样本预测分数的相对排序决定。在精确算术下预测相同，AUC 相同；浮点归约顺序可能产生小误差，接近并列的分数也可能改变排序，所以我们不会以数学重排直接声称浮点训练的 AUC 数字必然完全一致。

## Meta Revision 6：修正 Figure 4 的绘图错误

感谢审稿人指出 Figure 4 与公式 (5) 之间的不一致。我们复核后确认，Figure 4 的 Reduction 曲线误用了“只累计非空 owner 贡献”的计数，没有遵循公式 (5) 所描述的固定长度聚合 payload 模型。因此，问题在 Figure 4 的绘图数据与计数口径，我们将重新计算并重画该图，保留公式 (5)。

公式 (5) 的 $B D_i G$ 表示一个 local batch 中、每张表来自全部 $G$ 个参与 rank 的聚合向量 payload，因而不随该表的 pooling factor 或访问偏斜而变化。对同维度的表，在统一口径下其 Reduction 向量数应相同。若指标只统计实际跨 rank 的网络传输，则排除本地项后为 $B D_i(G-1)$；这属于“全部聚合 payload”与“仅远端 payload”的统计范围区别，不改变固定长度模型。
