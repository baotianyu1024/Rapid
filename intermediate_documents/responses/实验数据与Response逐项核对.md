## 1. 结论先看

1. Response 表 R2 的 Taobao 行中，Herald、TorchRec、BagPipe 与本次结果在表格显示精度下相同；RAPID、HET-GMP 接近但不完全相同。两个 Criteo 子集的所有方法数字都不同，不能断定旧数字正确或错误。
2. R8 的冷 ID 共现比例趋势相近，但输入及数量不同，四项均不是逐值复现。R3 只复现了一个增量路径和零旧 ID 迁移性质，无法验证四策略比较。R4–R6 只做了表内算术核对，R7 未逐项复验。
3. “RAPID+HugeCTR 较慢”指的是**本次 Criteo 的预热后训练过程也慢**：包含训练时 host 映射处理的 80 步平均时间约为每步 0.94–1.22 秒。它另外还有明显的启动开销；两者是分开的。现有日志没有将每步拆成数据读取、CPU 映射、传输、GPU 计算和通信，因此不能断言具体哪一项造成了多少慢。
4. 现有训练是实际的前向、反向和更新短程运行，但不是 response 所要求的严格端到端公平比较：初始化、batch 分区、表容量、模型细节和计时边界尚未完全对齐；未完成相同权重的逐层梯度及完整训练 AUC 验证。不能将这些数直接填入 R1 或精度表。

## 2. 实验对象和口径

- 数据均从公开源重新下载，本轮没有读取 `store`。Criteo Kaggle 和 Terabyte 各取 1,048,576 行，固定扩展为 26 表 multi-hot；Taobao 从三张 CSV 合并后抽取 1,048,576 行。Terabyte 用官方仓库 2015-02-15 分片，长窗口及共现实验用 2015-02-21 的 day6 分片。
- R2 为 CPU 回放和协议计数：8 个逻辑 rank、每 rank batch 8192、5 epoch、embedding dim 128、FP32，统计所有 rank 的 embedding 与梯度 payload，单位 GiB，不含 ID、metadata 和 dense 梯度；不是 GPU 实测通信流量。方法的缓存和同步语义不同，不是等显存预算排名。
- 八卡训练使用 V100-SXM2 32 GB，`NCCL_P2P_DISABLE=1`，日志显示 SHM 路径，未使用 NVLink。原先 V100 无法创建上下文是用户态驱动库与内核驱动版本不匹配，切换匹配库后八卡可用。
- Criteo 训练为 DCNv2 风格模型、dim 32、全局 batch 65,536；Taobao 为 DeepFM 风格模型、主 embedding dim 128。各自三次独立进程、预热 10 步、计量 80 步，SGD 0.001。Criteo 的 dim 32 与 response 文本中真实数据主 embedding dim 128 的目标不同，不能当作 R1 的同配置结果。

## 4. R3–R8：已核对什么，未核对什么

### R3 长窗口增量

新 day6 输入初始 2,097,152 行，再处理 56 个各 65,536 行窗口。第 56 窗结束有 66,939,261 个已知 ID；所有窗口旧 ID 的 owner 和 physical ID 变化均为零。最后八窗口平均每 rank 每步通信为 **249,303.94 向量**；response 的增量值为 **250,160.16**，差 -856.22，约 -0.34%。

这支持本次增量路径“旧 ID 不移动”和通信量级接近，不证明历史数据下数值相同。本次没有在同一输入重新运行纯 Unique、不更新原放置、全量重算三条对照，故不能核验 response 的 120.32%、29.88% 或其稳定性判据。此为 CPU 协议回放，不是 56 窗在线 GPU 训练。

R1 原表仍为待填。本轮只实现 Criteo 的 DCNv2 风格和 Taobao 的 DeepFM 风格训练，不涵盖 response 所列的全部模型、MovieLens 或合成负载；本次也没有完成配对种子、相同逻辑 ID 初始化、完整训练 AUC/LogLoss、统一显存和预处理总时间，因此这些项目均未验证。单机八卡运行不能证明多机扩展性。

## 5. RAPID+HugeCTR：启动慢还是训练慢？

**两者都有；此前“明显较慢”主要指以下排除启动及前 10 步之后的训练窗口。** 这里“训练窗口”包括各实现自身的训练时输入处理及前向/反向/更新；不是把离线规划和进程启动包含在内的完整项目端到端时间。每套框架统计边界有差别，以下数据不能作为严格同模型排名。

### Criteo 预热后训练时间

每步处理 65,536 样本。RAPID+HugeCTR 通过日志中第 10 步至第 90 步的墙钟时间相减除以 80；TorchRec 对每步输入切片、传输和训练同步计时；HET-GMP 采用每 10 步各 rank 最大墙钟时间。训练数据重复循环，因此 90 步不是 90 个互不重复的百万样本 epoch。

| 数据 / 方法 | 三次吞吐 samples/s | 三次平均每步 ms（约） | 三次平均吞吐 samples/s |
| --- | --- | --- | ---: |
| Kaggle / RAPID+HugeCTR | 63,743 / 63,769 / 69,932 | 1028.1 / 1027.7 / 937.1 | 65,815 |
| Kaggle / TorchRec | 876,169 / 875,439 / 868,587 | 74.8 / 74.9 / 75.4 | 873,398 |
| Kaggle / HET-GMP | 665,788 / 674,959 / 674,377 | 98.4 / 97.1 / 97.2 | 671,708 |
| Terabyte / RAPID+HugeCTR | 53,921 / 59,332 / 58,762 | 1215.4 / 1104.5 / 1115.3 | 57,338 |
| Terabyte / TorchRec | 839,931 / 863,873 / 840,362 | 78.0 / 75.9 / 78.0 | 848,055 |
| Terabyte / HET-GMP | 690,807 / 689,336 / 691,262 | 94.9 / 95.1 / 94.8 | 690,468 |

因此数字差异确实出现在预热后的训练窗口，而不是仅因初始化。它也不能直接证明 RAPID 算法或 GPU 通信本身慢：三个实现的计算图、初始化、表大小、输入流水和 HET 的 batch 成员并不完全一致。TorchRec 还出现 FBGEMM autograd 注册警告，梯度正确性须单独验证。

### 启动时间：有额外开销，但没有统一端到端计时

以 Kaggle 第一次 HugeCTR 运行日志为例：

| 日志事件 | 墙钟时间 | 含义与限制 |
| --- | --- | --- |
| 模型初始化第一条日志 | 03:56:44.495 | Python 脚本此前已读取映射文件计算表大小，时间未记录在该日志中 |
| reader 的 `schedule_h2d` 日志 | 03:56:49.742 | reader 配置阶段结束的日志点 |
| `Graph analysis` | 03:58:28.175 | 距上一日志约 98.43 秒；期间包含计划读取、哈希表构建/校验等，日志没有精确拆分，不能将全段认作纯映射时间 |
| 输出训练 source | 03:59:02.804 | 距 graph 日志约 34.63 秒，包含模型编译和初始化 |
| 第 10 步 | 03:59:14.893 | 前 10 步约 12.09 秒，包含首次运行预热 |
| 第 90 步 | 04:00:37.143 | 第 10 至 90 步 82.25 秒，即每步 1.028 秒 |

同样按 reader 日志到 graph 日志，Kaggle 三次约 98.43、96.76、97.27 秒；Terabyte 约 117.65、116.60、116.35 秒。各次 graph 到训练 source 约 34.5–34.7 秒。这些只是日志点之间的墙钟区间，彼此可重复但不是细粒度 profiler；Kaggle 映射 TSV 约 405 MiB、Terabyte 约 436 MiB。进程启动前的 Python 读映射、离线规划、输入预处理、下载、评估和 checkpoint 未纳入统一计时，也没有相同边界下其他框架的启动/完整训练总时间。因此不能量化完整端到端时间差。

当前 HugeCTR 的 reader 在 host pinned batch 上做样本重排与原 ID 到物理 ID 的哈希查找，再上传 GPU；每个 Criteo 样本的 multi-hot 总长度为 214。此路径是合理的性能排查对象，但没有 profiler 分段或去掉该映射的同模型对照，不能下结论说这就是训练慢的唯一原因，也不能把耗时直接归于 all-to-all 或 NVLink。HugeCTR 的 Unique 初始化修补后已跑通短训练，但未做修补前后的逐层梯度和通信性能对比。

## 6. 代码验证、证据和后续缺口

- RAPID `--mapping_only` 输出 embedding 原 ID/owner/physical ID 与样本序号；HugeCTR reader 在训练时加载计划。原始训练文件不变，但现有完整离线优化仍生成临时重排文件。
- 小样本 8 卡 Unique 模式运行 10 步，与单独生成的等价重排输入的 10 个打印 loss 一致；在线发布增量计划后继续训练的 10 步 loss 与预加载计划一致。只覆盖短程 SGD、单机和静态预留容量；checkpoint、其他优化器、多机和真实漂移未验证。
- 原始数据：`/mnt/nebula/cn-zhangjiakou/juicefs/longjiu.bty/rapid_experiment_data/fresh_datasets`；计算子集在 `/tmp/rapid_fresh_stage`，可能随临时目录清理。归档位于同一数据盘 `evidence_20261102/measurements.tar`、`runtime_plans.tar` 和两个 day6 summary JSON。
- Criteo 运行参数在 `code/run_criteo_benchmarks.sh`；映射说明在 `code/Rapid/docs/runtime_plan.md`；日志可在 `measurements.tar` 中按 `rapid_hugectr_*_run*.log`、`rapid_torchrec_*_run*.json` 和 `rapid_het_*_run*.metrics` 查阅。临时依赖与编译产物需在 `/tmp` 重建。
- 如要判断真正瓶颈，需在同一 HugeCTR 模型、相同输入和权重下，记录有/无 RAPID 映射的 host 调度、哈希查找、H2D、GPU 前反向、通信及等待时间；独立记录规划、启动和完整训练时间。再统一各框架模型、batch、初始化、优化器、数据与计时边界，先做梯度/更新和 AUC 检查，才能填写 response 的公平对照。
