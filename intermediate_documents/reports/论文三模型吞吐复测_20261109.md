# 论文三种主模型的 8 卡吞吐复测

按照论文 Table 1 / Figure 8 的数据集、模型类型、embedding 维度和 HugeCTR 主访问策略，复测 Kaggle/DCN（dim32、全 Reduction）、Terabyte/DLRM-DCNv2（dim32、全 Reduction）、Taobao/DeepFM（dim128、全 Unique）。Kaggle 的经典 DCN 分支依据本机 HugeCTR `samples/dcn/dcn_parquet.py` 构建：6 层 Cross Network、两层 1024 宽 deep 分支和 dropout；Terabyte 的 DCNv2 风格 shape 对齐 `code/Rapid/training/run_hugectr_dlrm.py` 的三层 Cross Network、512 投影及 `[1024,1024,512,256,1]` top MLP；Taobao 的 DeepFM 使用三层 400 宽 deep 分支、FM 二阶项和一阶项。Taobao 的主交互维度为 128，一阶稀疏项打包存储使物理表宽为 132。论文没有公布全部逐层参数，因此这些是有来源的同类型实现，不声明逐参数完全相同。

三组均为 8×V100-SXM2 32 GiB、每卡 batch 8,192、FP32、AdaGrad 0.01。各取已打乱的 983,040 条训练样本，重复 15 个 global batch 直至 510 步；HugeCTR 与 RAPID 在每组使用相同模型、优化器和逻辑数据。RAPID 的 Kaggle ACP 选择 25 Unique/1 Reduction，其他两组全 Unique。吞吐为完整训练循环 `510×65,536/FIT_SECONDS`，含前向、反向、更新与训练时数据路径，不含离线规划、初始化和验证。六次训练窗口 `FIT_READ_BYTES=0`。每格一次 GPU 运行；论文原值按 Figure 8 的图中标注换算。

| 数据／模型 | 当前 HugeCTR samples/s | 当前 RAPID samples/s | 当前加速 | 论文 HugeCTR / RAPID samples/s | 论文加速 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Kaggle / DCN | 625,151 | 2,032,420 | 3.251x | 601,000 / 1,840,000 | 3.062x |
| Terabyte / DLRM-DCNv2 | 546,769 | 1,329,655 | 2.432x | 569,000 / 1,386,000 | 2.436x |
| Taobao / DeepFM | 5,561,281 | 8,338,178 | 1.499x | 6,425,000 / 8,296,000 | 1.291x |

相对论文，Terabyte 的加速与双方绝对吞吐均接近；Kaggle 的加速较论文高约 6%，Taobao 高约 16%。当前设备是 32 GiB V100-SXM2，论文为 16 GB PCIe V100，且当前训练反复使用百万样本子集，因此数值接近也不是原环境及完整数据的逐值复现。

40 步 Nsight Systems 诊断把八卡 GPU kernel 累计时间除以 8 卡和 40 步，按 NCCL 与其他 kernel 分类。下表的“其他/NCCL”与论文 Figure 9 的“计算/传输”定义不同，只比较量级；GPU 并发 kernel 不能简单相加为互斥墙钟。吞吐以上面的无 profiler 510 步为准。

Taobao 的非 NCCL kernel 时间几乎等于论文计算时间，但 HugeCTR 的通信 kernel 较长；Kaggle 的模型计算比论文短，RAPID 的通信 kernel 仍较长。调整模型类型和维度解决了原先把 Terabyte 轻量 DLRM、Taobao dim32 与论文对照的错误，但没有消除硬件、数据切片与通信计划差异。论文 Figure 11 的通信向量计数应另按同一数据和前向/反向口径核对，不能用本表 kernel 时间代替。
