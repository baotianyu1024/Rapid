# HugeCTR 官方 T 系列生成与通信诊断（2026-11-03）

## 来源与构造

按 HugeCTR 固定版本 `61b4d539aa7044e9021896f0485be1a6697f4f44` 的 `benchmarks/embedding_collection/dataset` 和 `benchmark.sh` 核对。该目录的合成生成器是 `7table_470B_hotness20.py`、`180table_70B_hotness80.py`、`200table_100B_hotness20.py`、`510table_110B_hotness5.py`，没有独立名为 T20 的生成器；论文中的 T20 也可能指第 20 张表，不能据此另造一个 T20 负载。

本次直接调用后三种官方 Python 生成器。每个脚本以 Zipf 指数 1.1 采样各表 ID，对 Zipf 序号执行随机置换，产生随机二分类 label 和 13 个均匀分布 dense 特征；每个 `.part` 有 65,536 行。官网 `generation.sh` 对 100 个分片逐个生成后合并。T180 脚本将输出路径赋给 `output_file` 却使用 `output_filename` 写文件，执行前仅修复了该变量名；T200/T510 未改构造。官网生成器没有固定 NumPy seed，因此以下 SHA 标识本次实际生成数据，不代表官网规定的唯一字节序列。官方 T180 名称与脚本展开结果不同，实际有 177 张表，未补成 180 张。

生成入口为 `code/generate_official_t_shard.py`。它在每次生成前按分片预期字节数检查目标文件系统剩余空间，并检查可用 RAM；仅在 `/tmp` 写大文件。分片校验入口为 `code/audit_official_t_shard.py`，逐表核对 ID 上界、label 及 dense 有效性。三个分片均完成校验：

## 同一分片的通信诊断

按 response T 系列口径设 8 rank、每卡 512 行、每分片 16 个 global batch。假设每个 ID 的 owner 为 `ID % 8`，逐批逐表统计本 rank 访问、但由其他 rank 拥有的去重 ID 数；Reduction 的每卡远端向量数固定为 `512 × 7 = 3,584`。各表对 16 批、8 rank 的均值只做一次静态 ACP 选择。以下是**一个分片、一次遍历、全部 rank、FP32、前向加反向**的理论向量 payload，采用官网 `benchmark.sh` 的逐表 embedding 维度；不含 ID、metadata、dense 梯度及真实网络协议开销。

| 负载 | Unique/Reduction 表数 | 全 Unique GiB | 全 Reduction GiB | 静态 ACP GiB |
| --- | ---: | ---: | ---: | ---: |
| T180 | 100 / 77 | 107.739 | 65.625 | **48.658** |
| T200 | 150 / 50 | 58.682 | 83.125 | **34.163** |
| T510 | 490 / 20 | 51.762 | 223.125 | **27.031** |

逐表数据保存在各分片目录的 `hash_acp_audit_b512.json`。先前 `hash_acp_audit.json` 把整个 65,536 行分片当成一个 batch，得到 T180/T200/T510 的 26.912/20.375/19.866 GiB；其 batch 口径与 response 不同，**不得与本表或 response R2 混用**。本表采用简单 hash owner，没有执行 RAPID 放置、CPS、样本调度或其他四种方法的协议回放，也没有实测 GPU 网络字节；因此不能填入 R2 的 RAPID 或任何外部基线栏。若按同样模式重复 5 epoch，理论 payload 为本表的 5 倍，前提是每轮输入与策略不变。

## 全配置可运行性

官网完整数据有 100 个分片：T180 353.125 GiB、T200 111.426 GiB、T510 65.527 GiB。当前 `/tmp` 所在文件系统在本轮检查时约余 196 GiB，无法保存完整 T180；生成入口仍会在每次写入前重新检查。更关键的是，按官网**完整词表和逐表维度**仅 FP32 embedding 权重就需要：T180 247.109 GiB（理想均分 30.889 GiB/卡）、T200 386.916 GiB（48.364 GiB/卡）、T510 426.817 GiB（53.352 GiB/卡）。本机 8 张 V100 各 32 GiB；T200/T510 的权重本身已超显存，T180 每卡仅余约 1.1 GiB，无法容纳 dense 模型、梯度、优化器与通信缓冲。缩小词表或仅物化分片活跃 ID 可以运行另一种工作集实验，但不能称为官网完整配置的端到端吞吐。官方随机 label 也不适合精度保持实验。

因此当前完成的是按官网构造的真实分片生成、完整性验证和与 response batch 一致的 hash 通信诊断；T 系列正式端到端及多方法 R2 待有足够硬件或严格标注的缩减配置后再填。
