# 本地 batch 8,192：TorchRec 与 HugeCTR 显存、吞吐复测（2026-11-03）

## 本轮配置和判断

同一份重新下载并全局 shuffle 的多日 Criteo 分片子集，1,048,576 训练样本、26 表、128 维、DCNv2 风格、FP32、SGD lr=0.01、零 embedding 初始化，单机 8×V100 32 GiB，`NCCL_P2P_DISABLE=1`、`NCCL_IB_DISABLE=1`。本轮每卡 batch **8,192**、全局 batch **65,536**；数据仍为 `/dev/shm` 中的同一批紧凑 ID 样本，仅在训练入口按新 batch 重新切分，没有写新数据集。每轮 510 步且不做评估，吞吐按完整训练循环墙钟计算。原始 `train.bin` 与内存副本 SHA-256 均为 `ff5fd3c715bc222041d94c136844ee08749b14aa7cfda74f3767c1c786d42c6d`。

**HugeCTR 默认缓冲配置在 `model.compile()` OOM；按本数据的键数上界安全缩小两个独立缓冲后，可以完成同 batch 的真实 GPU 训练。** 实验前 8 卡均为空闲 V100，每卡约 32,448 MiB 可用；默认配置的失败不是其他训练进程占卡造成。下面的 HugeCTR 吞吐明确标记了所需缓冲参数，不能把默认配置的 OOM 当成慢吞吐。

| 8,192 本地 batch 配置 | 编译/训练 | 完整 510 步吞吐 | 显存/失败点 |
| --- | --- | ---: | --- |
| TorchRec 自动 planner，FP32 | 两次独立进程均完成 510 步 | **507,444 / 506,945 samples/s** | `torch.cuda.max_memory_allocated` 两轮最高均为 **4.74 GiB/卡**；运行中 `nvidia-smi` 一次采样最高 5,653 MiB |
| 原生 HugeCTR，26 MP，`DENSE_UNIQUE_RATIO=WGRAD_UNIQUE_RATIO=0.25` | 完成 510 步 | **321,611 samples/s**；第 200–500 步墙钟 **321,481** | 运行中 `nvidia-smi` 采样约 20.8 GiB/卡；`FIT_READ_BYTES=0` |
| 原生 HugeCTR，25 Unique + 表 20 Reduction，默认缓冲 | 完成 510 步 | **409,027 samples/s**；第 200–500 步墙钟 **409,267** | 运行中显存接近 32 GiB/卡；`FIT_READ_BYTES=49,152 B` |
| 原生 HugeCTR，照搬 TorchRec 的 18 DP / 7 table-wise / 1 row-wise，两个缓冲比例均为 0.5 | 完成 510 步 | **253,119 samples/s**；第 200–500 步墙钟 **252,924** | `FIT_READ_BYTES=0`；放置一致但 HugeCTR 仍用其自身 MP 通信协议 |
| 原生 HugeCTR，26 表全 MP、默认缓冲比例，FP32 | `model.compile()` 失败 | **无有效值** | `core23::SimpleCudaAllocator` 的 `cudaMalloc` 返回 out of memory |
| 原生 HugeCTR，照搬本轮 TorchRec 表放置 | `model.compile()` 失败 | **无有效值** | 同样在 GPU 分配阶段 OOM |
| RAPID+HugeCTR，使用旧 2,048 计划的物化输入，仅探测容量 | `model.compile()` 失败 | **无有效值** | 该计划 batch 不匹配，不构成 8,192 RAPID 吞吐实验 |

TorchRec 的 4.74 GiB 是 PyTorch 追踪的峰值张量分配；HugeCTR 的约 20.8 GiB 是运行中 `nvidia-smi` 的一次设备占用采样，两者不是同一显存统计口径，不能直接计算框架显存节省比例。

TorchRec 在本轮重算的自动计划为 **18 张 DP、7 张 table-wise、表 20 row-wise**，不同于本地 batch 2,048 时的 13 DP + 13 table-wise。DP 表为 1、2、3、4、5、6、7、8、12、13、14、15、16、17、18、23、24、25；table-wise 表为 0、9、10、11、19、21、22。不能把 2,048 的通信量和表策略搬到 8,192 的解释中。TorchRec 入口复用相同的 `input.bin`、`sparse.npy`，其 `input.json` 记录的是制备时的 2,048 batch，但实际 rank 切片、训练 batch 数和输出指标均由本轮命令行 `--local-batch 8192` 计算。

额外测试 HugeCTR 自带的混合通信压缩：只对 hotness=100 的表 20 使用 Reduction，其余 Unique。它无需缩容即可编译，完整训练比 HugeCTR 全 Unique 快约 **27%**，但仍低于本轮 TorchRec 约 **19%**（以 TorchRec 两轮均值为分母）。五个 100 步检查点的 HugeCTR loss 与全 Unique 在打印精度下一致。这是手工选择的单表消融，尚未对 8,192 全部表重新执行 ACP，不能称为最终最优 HugeCTR 配置。

## HugeCTR OOM 的进一步排查

- 默认原生 HugeCTR 输入设置完成后，`model.compile()` 调用 `core23/details/simple_cuda_allocator.cpp` 的 `cudaMalloc` 失败；未产生训练 step。把 TorchRec 的 18 DP、7 table-wise、1 row-wise 放置翻译为 HugeCTR EBC 放置后，**默认缓冲**同阶段仍 OOM；安全设置两个缓冲比例为 0.5 后才编译并完成训练。相同表放置下 HugeCTR 比自身全 MP 更慢，表放置相同并不意味着两实现使用相同通信协议。
- 通过 `code/trace_cuda_oom.c` 拦截 CUDA 分配，默认配置首次失败时，GPU 0 申请 **7,180,648,448 B**，只余 **3,754,360,832 B**。该申请恰好是 `65,536 × 214 × 128 × 4`，对应按全局 batch、总 hotness 和 embedding 维度预留的 dense MP 通信缓冲。仅设置上游 `WGRAD_UNIQUE_RATIO=0.5` 时仍申请相同 7.18 GB，故仅调整梯度缓冲不足以解决；源码另有 `DENSE_UNIQUE_RATIO` 控制 model/network 通信缓冲。
- 对全部 16 个 global batch 扫描原生紧凑 ID，按每表取最坏拥有者后相加，单卡原始键数上界相对上述最大键容量为 **0.1694**；去重只会降低实际需求。因此对本份固定数据用 **0.25** 同时设置 `DENSE_UNIQUE_RATIO` 和 `WGRAD_UNIQUE_RATIO`，高于审计上界，并完成 510 步、打印检查点 loss 正常下降。这个数据相关的缩容不能直接照搬到其他数据集或 batch；应先重算上界。
- 对 TorchRec 放置的 MP 表，逐表最大唯一键/最大容量比最高约 **0.3624**。仅设置 `WGRAD_UNIQUE_RATIO=0.5` 仍 OOM；同时设置 `DENSE_UNIQUE_RATIO=0.5` 后完成 510 步。两项 0.5 均高于上述数据上界；没有继续压低该混合放置的缓冲。
- RAPID 的 2,048 ACP 文件带有 batch 校验，直接给 8,192 训练入口会被正确拒绝。为仅检查模型容量，用 `--strategy unique` 跳过旧 ACP、保留旧物化 ID/表容量，仍在 `model.compile()` OOM。此测试**没有**重新执行 8,192 的 CPS/ACP，不能作为该 batch 的 RAPID 性能或通信结论。

## 本 batch 的通信量

分别在两框架进入训练循环前清零 NCCL API 计数，取前 30 步，按 communicator rank 排除 `peer==rank`；下面是**每卡每步逻辑 payload**，不是链路实际字节数。TorchRec 此时是新选择的 18 DP、7 table-wise、1 row-wise 计划，HugeCTR 为 26 MP，因此这个表用于解释本轮实际运行，不代表相同分片策略。

| 方法 | 远端 send | 远端 recv | AllReduce 输入 | 其他集合通信 API count 对应字节 |
| --- | ---: | ---: | ---: | ---: |
| 原生 HugeCTR，26 MP，缩容缓冲 | **487.79 MB** | **487.79 MB** | **64.18 MB** | 本次未见 AllGather/ReduceScatter |
| 原生 HugeCTR，25 Unique + 表 20 Reduction | **289.98 MB** | **289.98 MB** | **64.18 MB** | 本次未见 AllGather/ReduceScatter |
| TorchRec 自动计划 | **61.56 MB** | **61.56 MB** | **107.93 MB** | AllGather **4.19 MB**、ReduceScatter **4.19 MB** |

HugeCTR 全 Unique 的远端 `send/recv` 约为 TorchRec 的 **7.9 倍**；表 20 改为 Reduction 后降至约 **4.7 倍**，与吞吐提升方向一致。TorchRec 为更多 DP 表增加了 AllReduce 输入，但避免了大量 multi-hot lookup 向量跨卡分发；这与本轮 TorchRec 更高吞吐相符。AllReduce 的“输入 MB”不能与 `send/recv` 直接相加，亦不能当作 ring 实际链路字节。特别是 ReduceScatter 的 **4.19 MB** 是 API 的每 rank *输出分片* count，AllGather 的 **4.19 MB** 是每 rank *输入分片* count；它们都不是完整集合通信传输量。与 Response R2 的全体 rank、5 epoch embedding 协议估算的换算见[通信口径对账](TorchRec_R2与GPU通信口径对账_20261103.md)。分片策略和通信协议都不同，不能把吞吐差全部归因于某一个框架内核的效率。

## 为什么与此前的排序不同：当前 batch 的 GPU 时间线

此前报告中“更快”的对象主要是 **RAPID+HugeCTR**，并非本节的**原生 HugeCTR**。早期还曾把 HugeCTR 内部 `Time(10 iters)` 与 TorchRec 完整步墙钟混用；纠正后，本地 batch 2,048 的 Kaggle 是 RAPID **314,674** 对 TorchRec **300,618 samples/s**，Terabyte 是 RAPID **298,502** 对 TorchRec **329,287 samples/s**，原生 HugeCTR 分别只有约 **210,817 / 211,134 samples/s**。旧 Kaggle 8,192 的 RAPID **523,974** 对 TorchRec **520,246 samples/s**，两者接近；它用的是 Kaggle 和 RAPID 物理放置，不能代替当前多日分片子集的原生 HugeCTR。当前 8,192 的 RAPID 尚未重新完成 CPS/ACP，不能给它排吞吐名次。

对当前 8,192 配置，另用 Nsight Systems 在 `fit`/训练循环内采集前 30 步；按 8 张卡的 GPU kernel 时间求每卡每步均值，NCCL 和其他 kernel 各自取时间区间并集，重叠为两者交集。此诊断带 profiler，**吞吐仍以表中无 profiler 的 510 步结果为准**。

| 当前 8,192 配置 | NCCL kernel | 其他 GPU kernel | NCCL/其他重叠 | GPU kernel 忙碌并集 | 其中 SendRecv |
| --- | ---: | ---: | ---: | ---: | ---: |
| HugeCTR，26 Unique | **124.43 ms** | 77.92 ms | **0 ms** | **202.34 ms** | **100.83 ms** |
| HugeCTR，表 20 Reduction | **86.18 ms** | 73.63 ms | **0 ms** | **159.81 ms** | **62.53 ms** |
| TorchRec 自动计划 | **75.14 ms** | 75.31 ms | **22.86 ms** | **127.59 ms** | **17.73 ms** |

HugeCTR 两配置每卡各观察到一条执行 stream；TorchRec 每卡两条。HugeCTR 把表 20 改为 Reduction 后，远端 send 从 **487.79** 降至 **289.98 MB/卡/步**，对应 SendRecv kernel 从 **100.83** 降至 **62.53 ms/步**，NCCL 总时间下降约 **38 ms/步**；其他 GPU kernel 只下降约 **4 ms/步**。这比仅看总吞吐更直接地表明本轮原生 HugeCTR 的主要额外耗时在 embedding 通信。与 TorchRec 相比，HugeCTR 全 Unique 的非通信 kernel 时间接近，但通信时间多约 **49 ms/步**，且没有观察到 TorchRec 的约 **23 ms/步**通信计算重叠；两项合起来与无 profiler 的每步约 **204 对 129 ms** 差距同量级。它们不是可简单相加的独立优化收益，也不证明单改 stream 就能获得相同加速。当前测试禁用了 NCCL P2P/IB，不能把这一通信差距直接外推到启用 NVLink/P2P 或多机的环境。

上述 GPU 时间线仅核对 30 步，Nsight 会扰动执行；TorchRec 的实际计划是 18 DP、7 table-wise、1 row-wise，HugeCTR 的通信协议和模型算子实现未逐参数完全配对。诊断日志及导出的 SQLite 位于同一日志目录，文件名分别为 `nsys_hugectr_b8192_unique_30`、`nsys_hugectr_b8192_reduction20_30`、`nsys_torchrec_b8192_30`。
