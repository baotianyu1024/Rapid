# HugeCTR 与 RAPID 性能及正确性排查

> **最新对照**：后续 ACP 适配、缓冲区优化及三框架重测见 `端到端对照与ACP排查报告.md`；本文件保留当时的实验记录。

日期：2026-11-02。此前 `实验数据与Response逐项核对.md` 中的训练数值存在两个问题：数据读取及编译口径不公平，而且 Unique embedding 参数没有更新。旧数值只能作为排查线索，不应作为有效训练性能结果或填写 response。

## 1. AllReduce 从哪里来？原先的修复是否完整？

本次 Kaggle 配置的 26 张表全部由 ACP 配为 Unique。HugeCTR 将 sparse Unique group 标记为 `DenseModelParallelWithReduction`，模型并行前后向的 `DenseUniformModelParallelEmbedding` 使用 NCCL Send/Recv 实现的 all-to-all。此前修改 `HugeCTR/src/embeddings/embedding_collection.cpp`，将该类型纳入 `WgradInitializer` 的模型并行初始化分支，避免它落入后面的全词表 `AllreduceWgradInitializer` 分支。这修正了用户最初指出的初始化判断遗漏。

但进一步审查发现，初次修改不完整：`HugeCTR/src/pybind/model_pipeline.cpp` 的模型并行更新列表以及 `EmbeddingCollection::update_per_gpu(int)` 的通用更新列表都没有包括 `DenseModelParallelWithReduction`。结果是旧代码能完成前反向和打印 loss，但这些 Unique 表没有执行参数更新。现在两个更新列表均已补上该类型。

直接导出测试：8 卡、4 张各 8 行、dim 128 的表，全部使用 Unique，运行 3 步；同一初始化下，旧库四张表训练前后变化的 FP32 值数为 `[0, 0, 0, 0]`，修复后均为 1024。旧库测试通过 `LD_PRELOAD` 强制加载旧共享库并检查 `/proc/self/maps`；仅使用旧 Python 模块不够，因为它的 RPATH 指向新库。这个测试确认修复使参数更新发生，并非完整梯度正确性证明。

NCCL collective 日志对修复后的 Criteo 模型显示，训练期 AllReduce 为 **5,813,536 个 FP32 元素（约 22.18 MiB）**；bottom MLP、cross 和 top MLP 的参数按模型形状计算为 **5,813,441 个**，差 95 个对齐元素，大小吻合复制的 dense 网络梯度缓冲区。Kaggle 活跃 embedding 有 19,279,324 行、每行 32 个 FP32 值，总量约 2.30 GiB；日志没有显示这个规模的全表 embedding AllReduce。相应源码 `Model::exchange_wgrad()` 也确实对复制的 dense 网络梯度调用 allreduce；Unique 的模型并行路径有 Send/Recv。少量其他 AllReduce 还可能来自初始化/指标等，不应按内核名称单独推断来源。

时间线中 NCCL Send/Recv、AllReduce 内核的 GPU 活动显著，但该统计是跨 GPU 累加且有并发，不能直接换算为每步墙钟占比。时间线采集于补上参数更新之前，只用于观察当时的通信和等待，不能作为修复后完整训练正确性的证据。

## 2. 为什么原生 HugeCTR 和 RAPID 都慢？

实验采用相同 Kaggle 1,048,576 行、全局 batch 65,536、8 V100、dim 32、相同 DCNv2 风格模型和 Unique 配置。关闭 NCCL P2P，未使用 NVLink。下表的时间均以第 10 步至第 90 步的日志墙钟间隔除以 80 得到，包含各自的训练时数据处理，但不包含预处理、启动及规划；除三轮汇总外是单次排查结果。

| 对照 | 配置 | 约 ms/步 | 约 samples/s | 说明 |
| --- | --- | ---: | ---: | --- |
| 原生 HugeCTR | 旧构建、原始顺序紧凑 ID、默认直接 I/O | 423.55 | 154,730 | 旧版缺少 Unique 参数更新 |
| 物化 RAPID 输入 | 旧构建、先把相同样本调度/物理 ID 写入临时文件，关闭在线映射 | 429.80 | 152,480 | 与旧在线版打印 loss 一致；旧版缺少参数更新 |
| 原生 HugeCTR | Release、默认直接 I/O | 420.58 | 155,825 | 仅开启编译优化，I/O 仍占主导；此轮尚未补更新遗漏 |
| 原生 HugeCTR | Release、可选 buffered I/O、已补参数更新 | 81.91 | 800,073 | 前 10–20 步仍包含首次读盘，之后约 67 ms/步；单次 |
| 在线 RAPID | Release、buffered I/O、哈希查询、已补更新 | 324.77 | 201,789 | 源文件预热；单次 |
| 在线 RAPID | Release、buffered I/O、直接索引、8 映射线程、已补更新 | 109.14 | 600,490 | 源文件预热；单次 |
| 在线 RAPID | 同上，16 映射线程 | 96.64 | 678,163 | 单次，另两轮见下表 |
| 物化 RAPID 输入 | Release、buffered I/O、无在线映射、已补更新 | 49.86 | 1,314,334 | 同一 RAPID 样本及物理 ID；用于隔离在线映射，非原始输入训练方式 |

原生 HugeCTR 的 `BatchFileReader` 默认以 `O_DIRECT` 打开文件，绕过页缓存。该环境对临时 Kaggle 文件的顺序直接读取实测 956,301,312 字节 / 6.92845 秒，约 **138 MB/s**。每 global batch 约 59.8 MB，按此带宽估算约 0.43 秒，与原生实测 0.42 秒/步吻合，是强证据，但不是严格的逐步 I/O 分解。此前 TorchRec 使用 mmap 并受益于页缓存，不能把二者的旧数字当作同一存储条件下的纯框架比较。

已给该 reader 增加**可选** `HUGECTR_BUFFERED_IO=1`；默认仍保留原来的 direct I/O。buffered 模式适合允许系统页缓存且数据可反复复用的场景，缓存预热有开销，数据大于内存或冷盘时可能不会得到同样收益；Linux buffered AIO 的调度特性也与 direct I/O 不同。

旧 CMake 构建的 `CMAKE_BUILD_TYPE` 为空，实际主机 C++ 编译命令没有优化参数。改用 Release 后 C++ 和 CUDA 命令均包含 `-O3`。原生 direct-I/O 对照 423.55→420.58 ms/步，差别很小，说明编译优化并非原生读取慢的主要原因；但在线映射版在 direct I/O 下从旧版约 0.94–1.03 秒/步降至 0.482 秒/步，主机优化影响显著。不同版本的参数更新行为也已改变，不应将这个速度差当成严格性能归因。

原在线路径对每条样本的每个 embedding ID 做 `std::unordered_map` 查询；Kaggle 每 global batch 约 65,536×214 次查询。新实现按表构建直接索引，最多额外使用 1 GiB/计划实例，其他表保留哈希回退；原有映射唯一性、样本排列及增量扩展校验仍保留。默认 8 线程，可用 `RAPID_MAPPING_THREADS` 设为 1–128；本次使用 16。与有序预物化输入的 49.86 ms/步相比，在线版仍有约 47 ms/步的额外墙钟差，但这不是严格逐阶段 profile，因此不能把差值全部视为纯索引 CPU 时间。

## 3. 修复后重新测量

每行 8 卡、预热 10 步、测量 80 步、3 次独立进程，输入已通过 buffered 读取预热，RAPID 开启 16 映射线程，Unique embedding 更新已修复。每次循环使用相同百万样本子集；不是完整数据集训练。

| 数据集 / 模型 | 三次 ms/步 | 三次 samples/s | 平均 samples/s |
| --- | --- | --- | ---: |
| Kaggle / DCNv2 风格 | 96.64 / 94.14 / 99.11 | 678,163 / 696,173 / 661,228 | 678,521 |
| Terabyte / DCNv2 风格 | 96.65 / 100.20 / 102.96 | 678,076 / 654,052 / 636,504 | 656,211 |
| Taobao / DeepFM 风格 | 5.28 | 12,423,886 | 单次 |

Taobao 仅重跑一次；以上性能并未完成跨框架统一权重、网络、表容量、batch 和 GPU 计时边界的公平对照，也不应与旧的无更新版本当作完全相同工作量比较。先前 TorchRec/HET-GMP 结果仍只是参考。初次 Kaggle Release 直接索引构建在 reader 日志到 graph analysis 之间约 77.5 秒，且包含 TSV 加载、校验与索引构建；这个启动耗时及最多 1 GiB/实例的索引内存没有包含在上表吞吐中。

## 4. 一致性验证

- 用实际 `plan_smoke` 的两批原始记录，通过新 `RapidHostPlan` 转换后，与独立物化结果逐字节一致；增量新计划通过旧计划扩展检查。
- 大 ID 和合法 `UINT32_MAX` 物理 ID 的哈希回退、缺失 ID 报错分别通过独立小测试。
- 用同一小样本、相同初始权重、正确启用 Unique 更新，在线映射和物化输入均训练 10 步。训练前约 376 万个 embedding 权重逐值相同；训练后仅 5 个值存在浮点差异，最大绝对差 **2.33e-10**。该测试不覆盖完整数据、其他优化器、checkpoint 或多机。
- 真实 Kaggle 在线直接索引与物化对照的 10、20、…、90 步打印 loss 一致。完整训练 AUC、逐层梯度和优化器状态尚未验证。
