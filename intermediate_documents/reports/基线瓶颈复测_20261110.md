## BagPipe

Kaggle／DLRM、8 卡、local batch 8,192、dim32、AdaGrad 0.01、510 步，8 rank 全部完成，末步 loss 有限。

| 配置 | 最慢 rank 训练秒数 | 吞吐 samples/s | 缓存同步关键路径 ms／步 |
| --- | ---: | ---: | ---: |
| lookahead=8，cache=16M | 453.689 | 73,670 | 773.997 |
| lookahead=16，cache=32M | 268.325 | 124,563 | 367.701 |

原配置的清理频率为每 2 步一次。40 步分段计时显示，常规步的预取完成信号几乎立即到达，清理步的等待中位数约 1,440 ms。把清理周期改为每 4 步没有提速，预取等待变为每次约 3 秒。增大 lookahead 需要相应扩容缓存；只改 lookahead 会在初始化时报缓存形状不匹配。独立 NCCL 微基准对代表性的两组梯度归约约为 85 ms／步，说明缓存等待不能等同于 NCCL 传输时间。输入已预打乱并驻留内存，读取本身不构成该关键路径。

BagPipe 的在线 oracle 构建一个 Kaggle batch 的 ID 并集约需 121 ms，而内存输入获取约 0.03 ms。修正后的全窗口每步约 526 ms，因而除缓存同步外，在线预处理也占有实质份额。

原配置日志：`/tmp/rapid_bagpipe_recheck_20261110/kaggle_dlrm_8gpu_510steps/`；优化配置日志：`/tmp/rapid_bagpipe_la16_full_20261110/kaggle_dlrm_8gpu_510steps/`；分段计时：`/tmp/rapid_bagpipe_profile025_20261110/`。

## Herald

Kaggle／DLRM 的旧配置 510 步结果为 9,887 samples/s。每 rank 默认 16 个 LAIA 调度线程，共 128 个，而本机有效 CPU 亲和集合为 80 核。将线程数改为 8 后，独立 50 步从 392.18 秒降到 313.47 秒，但同配置的长跑前 150 步分别在 362.54、747.35、1136.20 秒完成，短跑提速不能直接外推。运行中 GPU 存在较长空闲段；对主进程每秒一次的 30 次栈抽样，两次观察窗口分别有 12 次和 25 次落在 Hetu 缓存同步／管理路径，也观察到参数服务器 barrier。栈抽样只能定位候选热点，不能直接当作时间占比。

进一步检查发现旧复现脚本设置 `cache_bound=0`，而 Herald 官方示例和 Executor 默认均为 100。`hetu_cache/src/cache.cc` 在缓存 embedding 的累计更新次数大于 `push_bound_` 时向参数服务器推送；阈值 0 会让每次更新都推送。已将复现脚本默认值修正为 100，旧 Herald 吞吐只能作为错误配置的诊断结果，不能作为最终基线。线程数为 8 的长跑在定位该错误后结束，未将其中的短窗口速度填入主表。

Kaggle／DLRM 在相同同步模式、16 个线程/rank 的 50 步对照中，阈值 100 的 8 rank 完整训练用时 316.88 秒，即 10,341 samples/s；旧阈值 0 的对应 50 步为 392.18 秒，即约 8,355 samples/s，提升约 24%。源日志：`/tmp/rapid_herald_bound100_20261110/kaggle_dlrm_50steps/`。

官方示例的 `bsp` 默认值为 -1，旧脚本使用 0。直接切换后，LAIA 稀疏输入给出 `(ID, 通信计划)`，而 `embedding_push_pull` 只接受 ID `NDArray`，因此发生 `TypeError`。已在 `cstable.py` 中参照 `embedding_lookup` 取二元组的 ID 部分。修复后的异步 50 步在 8 rank 完成，用时 301.19 秒，即 10,880 samples/s；末步 loss 范围为 0.5499–0.5725。源日志：`/tmp/rapid_herald_asp_fixed_20261110/kaggle_dlrm_50steps/`。

修正缓存阈值和异步接口后的独立 510 步训练在 8 rank 全部完成：最慢 rank 用时 3,195.625 秒，吞吐 10,459 samples/s，末步 loss 范围为 0.4921–0.5266。相对旧同步阈值 0 配置的 9,887 samples/s，提升 5.79%。短跑提升较大，但不能外推到 510 步；修复后的长跑仍受在线缓存和调度开销限制。源日志：`/tmp/rapid_herald_asp_fixed_full_20261110/kaggle_dlrm_510steps/`。

50 步日志：`/tmp/rapid_herald_recheck_20261110/kaggle_dlrm_50steps/`；长跑日志：`/tmp/rapid_herald_threads8_full_20261110.log`。
