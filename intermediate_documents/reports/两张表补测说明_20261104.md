# R1 吞吐与 R5 精度补测说明

## 测量口径

- 实际硬件为单机 8 张 V100 32 GiB；`NCCL_P2P_DISABLE=1`、`NCCL_IB_DISABLE=1`，避免 NVLink P2P 路径。
- 真实数据的本地 batch 为 8192，embedding dim 为 32。Kaggle、Terabyte、Taobao 各覆盖 DLRM、DLRM-DCNv2、Wide&Deep、DeepFM。
- 输入为全局打乱后保留的 983,040 行训练子集和 65,536 行留出集；训练重复读取子集至 510 步。大输入放在 `/dev/shm`，日志放在 `/tmp`，没有读取 `store`。
- R1 是实际 8 卡 GPU 的训练窗口 samples/s，不含预处理、规划、初始化和评估；当前表中的不同方法并非全部完成三次同口径测量。HugeCTR、TorchRec、RAPID 使用 AdaGrad 0.01；HET-GMP 共享 embedding 内核使用 SGD 0.01。
- R5 是 HugeCTR 全 Unique 与 RAPID 的五种子配对短训。两者使用相同 global batch、零 embedding 初始化、AdaGrad 0.01；AUC 为 65,536 行留出集上的精确值，差值区间是五对逐 seed 差值的双侧 95% t 区间。

## 可核对的结果

两张逐组合表见 [中文Response.md](中文Response.md) 的表 R1、R5a。原始来源是 [R1 基础结果](rowwise_d32_e2e_results_20261104.csv)、[HET-GMP DCNv2](het_d32_holdout_results_20261104.csv)、[HET-GMP 其他模型](het_d32_multimodel_results_20261104.csv)、[R5 逐次记录](r5_paired_d32_runs_20261104.csv)及 [R5 五种子汇总](r5_paired_d32_summary_20261104.csv)。EMBark 自动规划和 TorchRec 重复测量的补充结果分别写入 `embark_d32_e2e_results_20261104.csv`、`torchrec_rowwise_d32_repeats_20261104.csv`。

R1 的 105 个格子中，真实数据部分已有 84 个完整训练窗口 GPU 吞吐数字；其余格子保留明确的失败或不可测状态，不以通信回放或缩小词表数据代替。新增的 [EMBark 12 次测量](embark_d32_e2e_results_20261104.csv)全部完成 510 步、训练窗口 `read_bytes=0`。使用 HugeCTR 上游 EMBark 自动规划器，设每卡 embedding 预算 20 GiB、默认 `dp_threshold=0` 和 `dense_threshold=0`；规划结果在 Criteo 26 表、Taobao 4 表均为全 Reduction。这是官方规划器接入统一模型训练入口后的测量，不是上游原始模型脚本的吞吐。

[TorchRec 三次复测](torchrec_rowwise_d32_repeats_20261104.csv)覆盖全部 12 个真实数据组合，使用原 seed42 和新 seed43/44；最大相对标准差为 1.439%（Taobao/Wide&Deep）。第一版补测脚本漏设原成功实验中的 NCCL 预加载库，首个任务在 NCCL 初始化时 SIGSEGV；补齐 `/tmp/rapid_nccl_new/nvidia/nccl/lib/libnccl.so.2` 后，24 次新运行均完成。失败日志保存在 `/tmp/rapid_r1_torchrec_repeats_d32_20261104/kaggle_dlrm_seed43_nccl_init_sigsegv.log`，未进入统计。

R5 的 12 个组合全部完成，共 120 次 GPU 训练与留出评估。逐次记录中的最大训练窗口物理读取为 479,232 字节，仅两次非零。12 个配对差的 95% 区间均跨零；区间跨零不构成精度等价证明。Kaggle 的短训 LogLoss 较高，尤其 DLRM，提示重复使用约一百万行训练子集有明显过拟合风险。

在已完成的真实数据 R1 训练窗口中，HugeCTR、TorchRec、RAPID 的物理读取量远小于输入规模；HET-GMP 的主机输入与 GPU 常驻输入消融在 Kaggle/Terabyte DCNv2 上只相差 0.22%/0.29%。因此当前读盘不是这些配置的主要吞吐瓶颈；这个结论不等于所有框架的输入流水线已完全一致。

## 已测结果与仍有限制的项目

| 项目 | 当前证据与限制 |
| --- | --- |
| HET-GMP Kaggle/DeepFM | 原 BCE 在 SGD 0.01 下约第 300 步出现 NaN；改用数学等价的稳定 BCE 后完成 510 步，吞吐 816,947 samples/s，留出 AUC 0.565632、LogLoss 2.152135，但末步 loss 约 2.14，尚未收敛。SGD 0.001 的稳定性诊断为 817,867 samples/s、AUC 0.604916，学习率不同，未混入 R1 主配置。 |
| Herald | 依赖与 CUDA 路径修复后，三个真实数据集各四模型均完成 8 卡、510 步（12/12），结果见 [Herald CSV](herald_d32_e2e_results_20261105.csv)。Kaggle、Terabyte 的多热 LAIA 在线分配仍是主要吞吐瓶颈；早期 10 步诊断未用于 R1。 |
| BagPipe | 本地 trainer 增加 ragged multi-hot pooling 和优化器选项，修复标签导出与 CUDA 驱动库路径后，三个真实数据集各四模型均完成 8 卡、510 步（12/12），结果见 [BagPipe CSV](bagpipe_d32_e2e_results_20261105.csv)。早期 2/10 步探针标签错误，未计入正式表；Kaggle/DeepFM 和 Terabyte/DeepFM 的高 loss 不代表收敛。 |
| T180/T200/T510 完整官方词表 | 按 dim32、AdaGrad 权重/梯度/状态的理想均分下界分别需 50.56/37.17/40.01 GiB/卡，超过 V100 32 GiB。第 0 分片活跃工作集的 GPU 吞吐另见 [T 系列报告](扩展基线与T系列实测_20261104.md)，不能填入完整配置行。 |
| R5 全量最终收敛 | 现有五种子实验是 510 步、983,040 行重复短训；留出 AUC 和 LogLoss 有效，但不能当作全量数据的最终收敛精度或精度等价性证明。 |

BagPipe 修复后完成三个真实数据集、各四模型的 8 卡、510 步训练，逐 rank loss 均有限，汇总见 [BagPipe 结果](bagpipe_d32_e2e_results_20261105.csv)。Taobao 的 DLRM、DCNv2、Wide&Deep、DeepFM 分别为 2,064,385、1,981,837、2,096,891、2,199,542 samples/s；Kaggle 对应为 73,470、74,324、70,144、71,503；Terabyte 对应为 99,594、96,550、94,800、96,978 samples/s。Kaggle/DLRM 每步平均约 0.77 秒落在原生缓存同步关键路径，输入在训练前已解析并放入内存，因此这不是文件读取瓶颈。Kaggle/DeepFM 和 Terabyte/DeepFM 末步 loss 仍高，不能当成精度收敛。Kaggle/DLRM、DCNv2 的部分 rank 在记录全部 510 步、有限 loss 和总时长后退出时发生 core dump；该吞吐只反映已完整记录的训练窗口，不代表退出流程正常。已调整 BagPipe 缓存清理线程的退出顺序，后续组合正常退出。

Herald 的三个真实数据集各四模型均完成 8 rank、510 步，逐 rank 汇总见 [Herald 结果](herald_d32_e2e_results_20261105.csv)。Taobao 的 DLRM、DCNv2、Wide&Deep、DeepFM 依次为 415,450、424,153、434,392、441,185 samples/s；Kaggle 和 Terabyte 的八个组合也已正式完成。它使用原生 LAIA 在线样本分配与 Hetu GPU executor；参考网络形状对齐 TorchRec。多热 Kaggle/DLRM 的 10 步调度诊断约 56–105 秒，其中初始逐个插入 `flat_set` 和逐个建 `std::set` 对吞吐有明确影响；批量排序去重后短跑约 56–58 秒。这些短跑数值未填入 510 步表格。旧 BCE 在多热 DLRM 上因 sigmoid 饱和产生非有限 loss，已改为数学等价的两类 log-sum-exp 损失。共享本地 TopK 模式在 300 秒内未完成 10 步，正式运行使用非共享 LAIA。

2026-11-05 驱动库纠错：先前未设 `LD_LIBRARY_PATH` 的进程从 `/lib64/libcuda.so.1` 加载 **590.48.01** 用户态库，但节点内核驱动版本为 **550.54.15**，因此 8 卡的 `cuCtxCreate_v2` 全部返回 999；先前据此推断节点 GPU 故障是错误的。成功的 TorchRec/HugeCTR 脚本指定 `/usr/local/nvidia/lib64`，其中 `libcuda.so.1` 为 **550.54.15**。最小 CUDA 张量对照：默认环境失败，仅加 `LD_LIBRARY_PATH=/usr/local/nvidia/lib64` 即成功。内核日志中的 Xid 31/43 早于 2026-11-04 的成功训练，不能解释本次失败。BagPipe 探针脚本为 `code/probe_bagpipe_taobao.sh`，单卡日志位于 `/tmp/rapid_bagpipe_probe_20261105_1gpu/`；驱动路径修复后又处理了 NumPy 2 移除 `np.in1d`、探针缓存容量不足和上游退出线程不结束的问题，单卡两步损失分别为约 0.5271、0.4515。两步探针不能当作 R1 吞吐结果。

进一步验证：匹配 550 版用户态库后，Driver API 在 GPU 0–7 的 `cuCtxCreate_v2` 返回值均为 0。BagPipe 的 8 GPU / Taobao DLRM 探针使用每卡 batch 8192、dim32、PCIe 路径；8 个 rank 均完成 10 步并正常退出，日志位于 `/tmp/rapid_bagpipe_probe_20261105_8gpu/`。先前 `lookahead=2` 的长探针停在第三步预取等待，改为 `lookahead=8` 后通过；每 worker 的探针缓存增至 1,000,000 行以容纳全局 batch 预取。这是链路验证，既未验证 510 步稳定性，也未验证读取不成为瓶颈，不能据此填写 R1 的 BagPipe 吞吐。

数据正确性纠错：早期 BagPipe JSONL 导出器把 int32 标签按 float32 位模式解释，原始标签 1 被导出为约 `1e-45`；上述 2/10 步探针的 loss 和任何精度指标均无效。已将标签改为读取 int32 值，先写临时文件、检查剩余空间后再替换输入。Taobao 修正后首个 8192 行 batch 的正样本数为 415，与原始输入一致；Kaggle/Terabyte 同样从已打乱的原始输入重新导出。正式训练还使用与 TorchRec R1 相同的参考网络形状。

R1 中 HET-GMP 的共享表由 HetuTable 内部按 SGD 更新。仅把外层 dense optimizer 换成 AdaGrad 会得到混合优化器，无法构成与其他框架等价的 AdaGrad 对照，因此保留真实 SGD 口径。R5 的配对初始 embedding 取零，避免物理 ID 重排后随机初始化无法按逻辑 ID 对齐；随机非零初值的全量训练等价性仍需单独验证。
