## 环境和设备

8 × Tesla V100-SXM2 32GB，NVIDIA 内核驱动 550.54.15。系统默认 CUDA 590 用户态驱动与内核驱动不匹配，导致创建上下文返回 999；将 `/usr/local/nvidia/lib64` 放入 `LD_LIBRARY_PATH` 后，8 卡均成功执行 CUDA tensor 运算。为支持 sm_70，另配置 CUDA 12.4、PyTorch 2.6.0+cu124、TorchRec/FBGEMM 1.1.0；另用 NCCL 2.26.2 避免系统中旧 NCCL 八卡拓扑崩溃。设置 `NCCL_P2P_DISABLE=1` 后，8 rank AllReduce 正确得到 36；NCCL 日志记录各 rank 间使用 `SHM/direct/direct`，即经主机共享内存路径，不使用 NVLink。

固定提交的 HugeCTR 源码已修复 Unique 模式梯度初始化遗漏并编译、导入；用 Taobao 原始数据跑通 8 卡、10 步基础 HugeCTR 训练。该短测试只是环境和框架冒烟，尚未接入 RAPID，不是端到端吞吐对比。

## 集成进展

`code/Rapid/cps/generate_local_dataset.cpp` 增加 `--mapping_only`：输出表/原 ID/owner/物理 ID 对照和每 rank 原始样本序号，不重写数据集。两 rank、两 global batch 的固定测试通过，输出每个原始样本恰好一次且保留原 global batch。`experiments/export_runtime_plan.py` 可从完整离线优化阶段的中间结果还原最终计划并逐 batch 核对完整记录；Taobao 百万样本已导出并完成守恒检查。当前离线优化器仍会生成临时重排文件，最终训练从原文件加映射读取。

全新 HugeCTR 的 MultiHot RawAsync 数据读取支持加载此计划，在 host pinned batch 中完成样本调度及 embedding ID 映射，原始磁盘文件不变。使用 8,192 条 Taobao 输入、8 卡、Unique 模式运行 10 步，并与独立生成的同一重排输入比较：全部 10 步打印的 loss 相同。另用百万样本最终 RAPID 计划和原始输入完成 8 卡、10 步基础模型冒烟；这些短测试不构成正式性能对比。

`experiments/incremental/update_runtime_plan.py` 提供增量计划原型：在旧计划上追加新 ID 与 global batch，检查旧 ID owner/physical ID 和旧样本调度不变。测试追加 8,192 条样本及 24,126 个新 ID，旧映射前缀和新 batch 样本守恒检查通过。HugeCTR 可在 batch 边界等待并加载通过标记文件原子发布的新计划，加载前校验旧映射及样本序列均未改变；测试中第一步训练后切换，两批循环的 10 步 loss 与预先加载完整计划的运行一致。新计划不迁移旧 ID，SGD 参数保持在同一进程。增量启发式是明确标注的贪心局部性策略，不等同历史增量论文流程；输入文件和容量必须预先覆盖新数据，其他优化器、checkpoint 恢复及大规模在线运行尚未验证。

本报告中的运行是独立验证和工程测量，未证明 response 其余各表或完整训练精度。不能把不满足原表协议的数据直接填入 response。

## Taobao 八卡 DeepFM 初步训练测量

三套代码均实际运行 8 张 V100，原始输入为同一份 Taobao 百万行；local batch 8192、SGD 学习率 0.001、embedding 主维度 128。每次预热 10 步、测量 80 步，独立进程重复三次。禁用 NCCL P2P；本表的速率由实际批次样本数除以测量时长计算。

| 方法 | 三次吞吐量 samples/s | 平均 samples/s | 平均 step ms | NVML 单卡最高 GiB |
| --- | --- | ---: | ---: | ---: |
| RAPID + HugeCTR | 2,865,936 / 3,125,158 / 3,237,513 | 3,076,202 | 21.36 | 1.871 |
| TorchRec | 3,755,657 / 3,798,619 / 3,810,476 | 3,788,250 | 17.30 | 1.232 |
| HET-GMP | 9,714,434 / 9,797,944 / 9,823,646 | 9,778,675 | 6.70 | 1.861 |

以上为初步工程测量，暂不能填入 response 作为严格公平的端到端排名：三框架尚未对齐逻辑 ID 的初始 embedding 和所有权重，也未完成逐层梯度与收敛一致性验证；HET-GMP 原生分区会改变 batch 成员，且 rank 数据量不完全相等；TorchRec 和 HugeCTR 使用 132 维存储其中 3 维为填充，HET-GMP 使用 129 维；加载器、异步流水及性能计时边界不同。HugeCTR 的表大小按最终计划的物理 ID 上界分配，TorchRec/HET-GMP 使用此子集的活跃词表，均不是完整生产词表显存验证。NVML 是额外一次运行每 0.2 秒采样的全设备显存，包含上下文，可能漏掉短暂峰值。表中时长包含各自的训练时数据处理，尚未统一计入离线数据预处理和规划时间。结果可能受到同机 CPU 回放任务影响。

RAPID 早期单线程 host 映射仅约 0.44–0.52 M samples/s；并行化映射后上表为约 3.08 M samples/s。优化前后输出和在线更新的 10 步 loss 检查通过，但该短测试不能代替完整训练精度实验。

## Response 审核结论

R2 的 Taobao 三项基线按显示精度一致，RAPID 和 HET-GMP 接近；其他两个数据集存在差异，历史输入不可获取时不能判断原数字是否准确。R8 趋势得到独立支持，历史逐值未复现。R3 仅验证上述增量不迁移性质与数量级；R4–R7 的各项完整参数实验尚未逐项复验；R5、R6 存在空行，表注仍提到缺失的 HET-GMP 项，需修订；R1 和完整精度表仍缺符合原表协议的测量。CPU 计数不能证明 GPU 通信、吞吐或模型收敛；不应据此宣称 response 已全部验证。

HugeCTR 的修补点在 `code/upstream_fresh/HugeCTR/HugeCTR/src/embeddings/embedding_collection.cpp`：将 `DenseModelParallelWithReduction` 纳入模型并行梯度初始化分支。短测试证明修复后 Unique 路径可运行，尚无修补前后的逐层梯度及通信剖析，不能仅凭运行成功断言历史性能问题的改善幅度。

对 R4–R6 已有列还做了算术核对：R4 六行通信减少百分比与显示的向量数相符，R5 两个峰均比由表中数值计算后分别为 1.06908 和 1.20604，R6 两个权重峰值按 128×4 字节换算分别为 1379.320 和 172.415 MiB。四舍五入一致只验证表内算术，并不验证输入、放置或原始统计。

## Criteo 八卡 DCNv2 风格模型

两份重新下载的 Criteo 子集各取 1,048,576 条，固定 26 表 multi-hot 输入，global batch 65,536，FP32、SGD 0.001；三个框架各 10 步预热、80 步测量并在独立进程重复三次。模型包含 32 维 embedding、dense bottom MLP、三层低秩 cross 和 top MLP。NCCL 禁用 P2P。每种方法读取同一数据子集，但 HET-GMP 原生重分区改变 global batch，词表分配、初始化、cross 层实现、训练流水与计时边界不完全一致，尚未逐层对齐梯度和权重，也未验证完整训练 AUC；因此只作为工程观察，不能写成公平对照排名。TorchRec/FBGEMM 运行时给出 autograd kernel 注册警告，需单独验证 embedding 梯度。

TorchRec 计时包括输入切片与传输；HET-GMP 以每十步各 rank 最大耗时计算；HugeCTR 使用日志中第 10 步至第 90 步的时间戳，包含在线映射但排除初始化与离线规划。这些计时方式不同，所有吞吐均不含完整预处理与规划。大表计划每次启动需解析 400 MB 以上文本映射，代价明显。`code/run_criteo_benchmarks.sh` 保存本次运行参数。

| 数据 / 方法 | 三次吞吐量 samples/s | 平均 samples/s |
| --- | --- | ---: |

在当前实现及测量口径下，RAPID+HugeCTR 的 Criteo 吞吐明显较低。当前 host 映射处理是需要重点剖析和优化的可能瓶颈，但本次未做足以确定瓶颈归因的性能剖析。Kaggle 初始化期间观测到 HugeCTR 单卡约 16.5 GiB 的设备占用，包含预留与上下文，不是统一峰值显存测量。不同系统输入预处理和表大小也不一致，不能将该表当作等模型、等显存、等精度的严格对照。
