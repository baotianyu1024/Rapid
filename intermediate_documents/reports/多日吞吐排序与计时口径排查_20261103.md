# TorchRec 与 HugeCTR 吞吐排序排查（2026-11-03）

> **后续深入复核：** 本报告的旧计时纠错有效，但“GPU 通信/计算调度是主要差异”的归因当时没有导出 TorchRec 实际逐表计划，也未按 NCCL communicator 排除本卡发送，结论不完整。逐表计划、真实远端 NCCL payload、同放置协议对照和修正解释见《TorchRec_HugeCTR吞吐与通信复核_20261103.md》。应以新报告为准：TorchRec 默认 13 张小表 DP + 13 张大表 table-wise，RAPID 是 26 表 MP；RAPID 与 TorchRec 默认计划的远端发送分别约 26.56 和 26.69 MB/卡/步，几乎相同。

## 结论与纠错

此前《Response_R1_R5真实GPU续测_20261102.md》把 HugeCTR 的内部 `Time(10 iters)` 换算值与 TorchRec 完整 step 墙钟值直接比较，造成 RAPID 吞吐优势被高估。HugeCTR 在每个打印块结束后获取 loss、打印并启动下一块，这段时间不在 `Time(...)` 内，却实际占用训练墙钟。第 30 至 110 步的同一批日志时间戳重算后，Terabyte/DCNv2、本地 batch 2048 的 RAPID **低于** TorchRec；先前“略快 0.24%”的结论撤回。Kaggle 本地 batch 2048 的优势约 **4.7%**，不是 15.77%。旧表内部计时值仍可用于 HugeCTR 自身的同口径消融，不能与 TorchRec 直接排名。

| 数据集 / 方法 | 旧内部计时 samples/s | 第 30--110 步墙钟三轮 samples/s | 墙钟均值 |
| --- | ---: | --- | ---: |
| Kaggle / 原生 HugeCTR | 233,266 | 210,794 / 210,862 / 210,794 | **210,817** |
| Kaggle / ACP-only | 330,115 | 298,638 / 298,774 / 298,501 | **298,638** |
| Kaggle / RAPID+HugeCTR | 348,014 | 314,699 / 314,623 / 314,699 | **314,674** |
| Kaggle / TorchRec | 不适用 | 原逐步计时 300,433 / 302,016 / 299,406 | **300,618** |
| Terabyte / 原生 HugeCTR | 233,671 | 211,100 / 211,202 / 211,100 | **211,134** |
| Terabyte / RAPID+HugeCTR | 330,070 | 298,842 / 297,959 / 298,706 | **298,502** |
| Terabyte / TorchRec | 不适用 | 原逐步计时 329,649 / 328,388 / 329,823 | **329,287** |

墙钟公式为 `80 * 16384 / (timestamp(iter=110) - timestamp(iter=30))`，日志时间戳只有毫秒精度，表中个位数不应解释成统计精度。80 步中 RAPID 内部计时约 3.97 秒，完整墙钟约 4.39 秒，漏计约 0.42 秒（约墙钟的 9.6%）。Kaggle 本地 batch 8192 的 RAPID 日志墙钟复核均值约 **523,974**，TorchRec **520,246** samples/s，接近持平；旧报告的 11.50% 优势同样无效。

## 同配置复测：数据与计时

用当前三天 Criteo 分片子集、26 表、128 维、8 张 V100、全局 batch 16,384、SGD lr=0.01、零 embedding 初始化，关闭评估，测 510 步。HugeCTR 以第 200--500 步日志时间戳计算；TorchRec 的同区间数值来自逐 step 累计，另记录完整训练循环墙钟。**跨框架更接近的比较是 HugeCTR 整段 `FIT_SECONDS` 约 297,167 对 TorchRec 整段循环 324,349 samples/s**；窗口列可用于各自实现内部消融，不能把 TorchRec 逐 step 数值直接当成同边界墙钟排名：

| 方法 / 输入路径 | 第 200--500 步 samples/s | 510 步参考口径 | 输入设置 |
| --- | ---: | --- | ---: |
| RAPID+HugeCTR 在线映射 | **299,269** | `FIT_SECONDS` 含启动初期，约 297,167 samples/s | 73.53 秒 |
| RAPID+HugeCTR 预物化 | **299,342** | 与在线映射 loss 在打印精度下一致 | 7.19 秒 |
| RAPID+HugeCTR 在线映射，打开 `train_intra_iteration_overlap` | **300,734** | 打印的 loss 与原配置一致；单轮诊断 | 68.13 秒 |
| TorchRec 锁页预取 | **332,795（逐 step 累计，非窗口墙钟）** | 逐 step 324,508；完整训练循环墙钟 **324,349** samples/s | 含在进程启动阶段 |

在线映射与预物化的稳态差仅约 0.02%，因此这里在线映射主要增加**初始化时间**，不是稳态训练的主要瓶颈。打开 HugeCTR embedding 的 intra-iteration overlap 后，单轮墙钟提高约 **0.5%**，仍低于 TorchRec；该开关针对 embedding 路径，不等于把 dense 梯度 AllReduce 移到独立 stream，且单轮差异不应视作稳定加速。用现在的代码重跑旧 Terabyte 输入，HugeCTR 第 200--500 步墙钟同样为 **299,269** samples/s；新数据分布不是吞吐排序变化的主要原因。另以旧输入、相同 510 步把学习率从 0.001 改为 0.01，并保持零初始化，短窗口内部计时约 330,189/330,388 samples/s，墙钟两轮均约 298,706；学习率及零初始化也不能解释约 10% 的计时差。以上各组并非严格逐参数相同的跨框架模型，结论限于这套实现和配置。

## Shuffle 与读取检查

`code/Rapid/experiments/reproduction/scripts/prepare_criteo_parquet.py` 对三个训练日期来源的 10,019,245 行无放回抽取 1,048,576 行，再以 `RandomState(20261103).permutation` 对**全部输出行** shuffle；不是仅每个 batch 内 shuffle。HugeCTR reader 日志的 `shuffle=OFF` 指运行时不再次打乱，输入文件已全局 shuffle。原始 `train.bin`、RAPID 计划输入和 `/dev/shm` 训练副本的 SHA-256 均为 `ff5fd3c715bc222041d94c136844ee08749b14aa7cfda74f3767c1c786d42c6d`。TorchRec 使用相同样本的紧凑 ID 副本；原生 HugeCTR 的标签与 dense 列逐条相等；RAPID runtime plan 的 `full_record_audit=true`。因此训练样本和顺序已经核对，物理 ID 不能直接按字节跨实现比较。

当前复测训练窗口的 `/proc/*/io` `read_bytes` 增量为 **0**；旧四框架短窗口报告中的有效 rank 也为 0。TorchRec 把输入预置 GPU 的旧消融，相对常规锁页预取仅提高 Kaggle **1.47%**、Terabyte **1.08%**；GMP 预置稀疏 ID 后 Terabyte 只提高 **0.09%**。物理磁盘读取不是本次瓶颈；单凭 `read_bytes=0` 不能排除 CPU 处理或 H2D，但预置实验与在线/预物化消融未显示足以解释排序的输入路径成本。这里的结论只适用于内存驻留的 1M 子集循环训练，不能外推为全量数据流式读取已解决。

## GPU 时间花在哪里

Nsight Systems 对 `fit` 内 30 步进行诊断。HugeCTR 每卡观察到 1 条执行 stream，NCCL 与非通信 kernel 没有重叠；TorchRec 每卡观察到 2 条 stream，通信与非通信 kernel 的重叠平均约 **0.342 秒 / 30 步**。HugeCTR 的 dense 梯度 `ncclAllReduce` 每卡每步 1 次，单次平均 **23.59 ms**，占所捕获 GPU kernel 时间 **43.6%**；embedding SendRecv 占 **18.0%**。TorchRec AllReduce 在独立 stream，上报平均单 kernel 7.15 ms，约每卡每步 4 次，并与计算重叠。两框架 kernel 数和张量拆分不同，不能直接把单 kernel 时长相减当成可实现的加速。Nsight 诊断会扰动运行，以上比例只用于定位，吞吐采用不带 profiler 的日志。

HugeCTR 的 `code/upstream_fresh/HugeCTR/HugeCTR/src/core23_network.cpp` 中 `Network::exchange_wgrad()` 明确对 dense `wgrad_tensor_` 做 AllReduce；它不是 Unique 表反向通信 bug 的再次出现。当前多日 RAPID ACP 为 **26 Unique、0 Reduction**，仍有这条 dense 梯度 AllReduce。后续实测发现两实现的公共 dense AllReduce 输入同为约 **64.18 MB/卡/步**，TorchRec 的 NCCL kernel 总时间也没有更短；差距需结合实际表计划、协议和计算重叠解释，详见新报告。打开 HugeCTR embedding 重叠开关一轮仅提高约 0.5%。

## AUC 达标时间的解释范围

同一独立验证日期、每 100 步检查一次、首次 AUC≥0.65：TorchRec 第 6,800 步 **368.988 秒**，RAPID 第 5,600 步 **433.814 秒**，原生 HugeCTR 第 5,600 步 **490.554 秒**，时间从训练进程启动计。RAPID 的离线规划与导出另至少 **22 分 19 秒**。TorchRec 即使多用 1,200 步，仍因本配置实际每步更快而先达标。跨框架 dense 初值和部分算子未逐值配对，不能把达标步数差归因于 ACP 或 embedding 放置；末段 AUC 仍上升，不能称为最终收敛 AUC。
