# Kaggle 批间通信量与 CPS 顺序偏置排查

日期：2026-11-02。此次检查使用重新下载的公开数据，没有读取 `store`。先前的表 20 结果和固定策略吞吐见《Kaggle_CPS后ACP重新核验.md》；本文分析其 batch 差异，不能把同一数据上拟合与评估的结果当成对完整 Kaggle 泛化的证明。

## 数据是否全量 shuffle

没有。此前实际流程是先取原始 Kaggle `train.txt` 的前 1,048,576 行，转成固定 multi-hot，再对这 1,048,576 行以 `RandomState(42)` 洗牌；不是对完整 45,840,617 行训练集洗牌后再取子集。脚本 `code/audit_kaggle_shuffle_source.py` 从原始输入独立读取此前缀，用 seed 42 重建排列后逐行比较所有 1,048,576 条样本的 label 和表 20 第一 ID，错误分别为零，确认子集内部洗牌的具体方式。这个核对不能证明原始完整数据不同位置分布相同。

## 差异从哪里出现

对于此前那 16 个 global batch、表 20：

| 统计 | 各 batch 的 8 rank 平均或全局值范围 |
| --- | ---: |
| 每个 global batch 不同 ID 数 | 2,383,227–2,426,830 |
| 原始 hash 放置下远端 Unique，8 rank 平均 | 366,003.625–370,866.625 |
| 最终 CPS 后远端 Unique，8 rank 平均 | 32,640.375–68,706.000 |

完整逐批各 rank 统计由 `code/audit_kaggle_batch_drift.py` 独立从同一份物化记录重算，保存在 `/tmp/rapid_kaggle_drift_audit.json`；CPS 前后每个 global batch 不同 ID 数一致。原始 hash 和 global batch ID 数基本平稳，而最终 CPS 的远端访问显著上升，说明这个斜坡是在本次 CPS 规划及调度后出现，而不是计数时由于源 batch 的不同 ID 数增加造成。

固定最终 CPS 的 embedding owner 与每条样本分配的 rank，不重新规划，仅在每个 rank 内把样本跨 batch 洗牌，重新组合 global batch，进行三个种子诊断。各 batch 8 rank 平均远端 Unique 范围分别为 51,561.75–52,606.125（seed 42）、51,151.0–52,270.125（seed 123）、51,299.75–52,396.625（seed 2026）。这改变了 global batch 的样本组成，不能当作原实验的真实训练或全量 shuffle；它说明显著斜坡与样本分组和固定 CPS 放置的关联有关。

## 倒序重新规划实验

重用相同 1,048,576 条样本及同一 hot ID 集，只把原始 16 个 global batch 的顺序反过来，每个 batch 内记录完全不变；16 对 batch 的 SHA256 均已逐项核对。使用相同的 `arrange_ids_to_devices` 和 `generate_local_dataset` 参数重新运行初始 CPS 放置和调度，再按原脚本统计表 20 远端 Unique。

| 初始 CPS 规划顺序 | 前 4 个处理批次平均 | 后 4 个处理批次平均 |
| --- | ---: | ---: |
| 原始顺序 | 37,584.0625 | 81,133.09375 |
| 完全倒序 | 35,547.5625 | 80,688.3125 |

原顺序初始 CPS 全 16 批平均是 60,427.875，倒序重新规划是 59,939.4921875；两者都高于 57,344，按远端平均通信模型应选择 Reduction。此前报告的 51,158.2578125 是同一前缀输入经过额外 owner/sample 优化后的最终计划，才降到阈值以下并选择 Unique。故本次之前“CPS 后全 Unique”的表述没有区分初始 CPS 与额外优化，不能被理解为论文原始 CPS 的直接结论。

按批次一一对照：原批次 0 在原规划中为 32,961.125，倒序后作为第 15 批为 84,846.25；原批次 15 在原规划中为 84,649.0，倒序后作为第 0 批为 28,261.125。两次规划结果的物理放置与样本 rank 分配可以不同；正是这项对输入规划顺序的依赖被测出。该试验使用初始 CPS，不含后续 owner/sample 优化，与先前最终 CPS 数值不是同一个阶段。

这一结果表明先处理的 batch 在这份离线计划中得到显著更好的 locality；只看先前 16 批平均掩盖了样本顺序敏感性，也提示同数据规划与评估可能过于乐观。它不能单独证明此前 Unique/Reduction 吞吐差距完全由该偏置造成。

## 代码和出现过的 ID

当前 `code/Rapid/cps/arrange_ids_to_devices.cpp` 顺序扫描 global batch：每批根据已注册的冷 ID 放置及此前累积的 device 大小分配样本，再把新 ID 绑定到首次关联的 rank，并根据累积访问计数进行迁移。后续基于同一训练 trace 的 owner 细化和样本调度也不会消除顺序效应。这个设计有明确的输入顺序依赖；当前实验证明实际实现存在很强的顺序偏置，但尚不能证明某一行存在与论文算法不符的实现 bug，也不能只据此判断论文全部实验。

**已确认的论文复现缺口：**论文第 5.2 节第 2 步要求用子图聚类（例如 METIS）初始化放置。当前程序支持 `--seed_assignment`，但此前 `placement.command.json` 未传这个选项，也未加载初始化 checkpoint；因此此前实验没有执行论文所述的子图初始化。不能将本次无种子 CPS 的顺序偏置、ACP 表 20 选择或吞吐直接视为论文完整 CPS 的复现。这是实验流程缺失，不是已经证明的单行代码 bug；仍需相同数据下的有/无种子对照，才能判断初始化对偏置的影响。

以最终 CPS 计划为例，在本实验规划流中，首个 batch 的表 20 全局不同 ID 为 2,409,811，均是此前未出现的 ID；最后 batch 全局不同 ID 为 2,403,895，其中首次出现 704,587。末批每 rank 平均 68,706 个远端 Unique 中，约 66,942.875 来自此前出现过的 ID、1,763.125 来自首次出现的 ID。这里“首次出现”以本次洗牌后 16 批的处理顺序为准，不能等同于真实生产时间或全数据历史。分析脚本 `code/audit_kaggle_novelty.py`。

## 全训练集均匀随机抽样对照

对公开 Kaggle 原始训练集计数共 45,840,617 行，使用 `default_rng(2026)` 从全体行均匀无放回抽取 1,048,576 行，按 seed 42 打乱该样本并按相同转换脚本构造 multi-hot；这在抽样分布上等价于对完整训练集做均匀随机排列后取前 1,048,576 行，但并非把全部 4,584 万行转换后进行完整训练，也不是与此前前缀样本相同的排列。抽中原始行号及其 SHA256 保存在结果中。所有数据写入前检查目标容量，样本在 `/tmp` 构造，数据盘的持久副本逐文件 SHA256 验证。

使用和倒序试验相同的初始 CPS 放置与样本调度（未启用 METIS 种子，也未运行此前最终 owner 优化），测得表 20：

| 配置 | 16 batch、8 rank 平均远端 Unique | 前 4 批平均 | 后 4 批平均 | 单 batch 平均范围 |
| --- | ---: | ---: | ---: | ---: |
| 原始 hash | 393,317.5234375 | 393,385.25 | 392,724.5 | 391,563.125–395,719.5 |
| 初始 CPS | 77,350.9296875 | 43,228.3125 | 106,439.625 | 35,370.375–111,304.0 |

初始 CPS 的表 20 平均远端 Unique 77,350.9296875 高于相同远端口径的 Reduction 57,344，静态通信量规则因此选择 Reduction，与论文和用户的选择方向一致；它没有逐值复现用户的 68,493.41。重新从完整训练集均匀抽样后，hash 仍稳定而本次 CPS 的顺序斜坡仍在，说明该斜坡并非仅由前缀样本造成。两组因数据和后续优化阶段不同，不能把此数与此前最终 CPS 的 51,158.2578125 差值直接视为抽样的单一因果效应。

均匀抽样的 912 字节记录持久副本位于数据盘 `rapid_experiment_data/fresh_datasets/criteo_kaggle_uniform_1048576_seed2026.bin`，SHA256 为 `0c971ffa05d48c08aed81e17dbf395c725f11191b967d639b8b19e1bc1292aec`。结果 JSON 保存在 `/tmp/rapid_kaggle_full_sample_audit/results.json`。

## 一种 METIS 种子对照

在此前前缀样本的 1,048,576 行范围内，以 seed 42 均匀抽 10 行（约 0.00095%，与论文 0.001% 示例同数量级），排除 hot ID，构造冷 ID 共现图并使用 `pymetis 2025.2.2`、8 分区和 METIS seed 42；形成 818 个冷 ID 的初始化放置。它是依据论文描述构造的一个具体方案，不声称为作者的原始种子或参数。

用与原始初始 CPS 相同的样本顺序及其他参数，只增加 `--seed_assignment`：无种子的前/后 4 批平均远端 Unique 分别为 37,584.0625 / 81,133.09375；此 METIS 种子方案为 **36,433.375 / 81,600.65625**，全 16 批平均 60,465.5546875。该方案中顺序斜坡依然存在，且平均数仍高于 57,344。种子样本仅 10 行、818 个 ID，不足以证明更大图、其他种子或完整论文初始化也无效；需要多种子与独立留出数据进一步验证。

本次重算通信量为按远端去重 ID 的 trace 模型，不是链路字节；没有使用新的全训练集随机样本重新跑四框架 GPU 吞吐，不能直接沿用旧端到端表作为新样本结果。
