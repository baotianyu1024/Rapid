# RAPID、HugeCTR 与 TorchRec：通信、吞吐排序和传输路径核对

## 先对齐实验

`中文Response.md` R2 的 Terabyte **RAPID 45.468 GiB < TorchRec 111.127 GiB**，是本地 batch 8,192、8 rank、5 epoch 的 **CPU 回放 embedding 协议总量**，排除 dense 梯度、ID/metadata、计算时间和初始化。二者前向与反向各跨端传输只计一次。它不是相同 batch 的 GPU 端到端吞吐测量。当前多日 Criteo、128 维、本地 batch 8,192 的 RAPID CPS/ACP 尚未重新完成，旧 2,048 计划的容量探测在 `model.compile()` OOM；因此没有有效的 8,192 RAPID 对 TorchRec GPU 吞吐排名。

已完成的更接近同配置 GPU 对照在本地 batch **2,048**：RAPID+HugeCTR 完整 510 步训练循环约 **297,167 samples/s**，TorchRec 自动计划两轮 **324,349 / 325,784 samples/s**。但这个 batch 的 RAPID 26 MP 与 TorchRec 13 DP + 13 table-wise 实测远端点对点 `send` 分别为 **26.56 / 26.69 MB/卡/步**，几乎相同；不能把 R2 的 8,192、5 epoch、全部 embedding 通信减少 59.08% 直接用来解释 2,048 的运行时排序。R2 总量与运行时 API 计数的换算另见《TorchRec_R2与GPU通信口径对账_20261103.md》。

## 通信更少为何仍可能较慢

在上述 **2,048** 的 Nsight 30 步时间线中，RAPID+HugeCTR 的 NCCL kernel 时间 **33.34 ms/步**、其他 kernel **20.78 ms/步**，未观察到两者重叠，GPU 忙碌并集 **54.11 ms/步**。TorchRec 对应为 **35.39 / 23.87 ms/步**，但有 **11.39 ms/步**重叠，忙碌并集 **47.86 ms/步**。因此 TorchRec 即使没有更短的 NCCL kernel 总时间，也能以较短的 GPU 关键路径完成这组训练。两实现的表放置、通信协议及部分模型算子尚未逐参数严格配对；时间线定位了原因组合，不能单独把全部差距归因于 stream 调度。

RAPID 在线映射与预物化在 2,048 的稳态吞吐接近，说明当前内存驻留子集的每步在线映射不是主要稳态瓶颈；但在线输入设置另约 **73.53 秒**，离线规划与导出另至少 **22 分 19 秒**。若“端到端”包含进程启动、计划准备或短作业总时间，RAPID 更可能落后；前述 297k/324k 只比较训练循环。旧 Kaggle 8,192 的稳态 RAPID **523,974** 对 TorchRec **520,246 samples/s**，实际接近持平；它不是当前 Terabyte 8,192 R2 的同一端到端实验。

## 之前 TorchRec 比原生 HugeCTR 慢，为何现在反过来

早期 **32 维、local batch 8,192** 的工程表，Kaggle 原生 HugeCTR 全 Unique **984,456**、TorchRec **784,350 samples/s**；当时 TorchRec 每步从 CPU 原始数组切片、构造 KJT、H2D，预热只有 10 步，而且首轮 **610,109** 明显低于后两轮 **880,139 / 862,800**。同一数据上的输入消融显示，TorchRec 原始数组每步处理约 **99.90 ms**，预格式化锁页批次约 **55.33 ms**，异步预取约 **53.59 ms**。后来按内存驻留输入公平性方案、预热 30 步重测，Kaggle TorchRec 预取 **1,230,607**，原生 HugeCTR 全 Unique **979,506 samples/s**；即使把 TorchRec 全部输入预放 GPU，仅再提高约 **0.9%**。原先的“原生 HugeCTR 更快”是旧输入路径和测量设置下的结果，不能当成固定的框架排序。

另一个混淆是早期把 HugeCTR 内部 `Time(10 iters)` 换算吞吐与 TorchRec 完整步墙钟直接对比，漏计 HugeCTR 打印块之间约 **9.6%** 的墙钟时间；Terabyte 2,048 的旧“RAPID 略快”已经撤回。后续 128 维测试又改变了 embedding 宽度、global batch、TorchRec planner 的逐表策略、初始参数与训练区间。当前 8,192 的原生 HugeCTR 全 Unique **321,611** 对 TorchRec **507,444 / 506,945 samples/s**，是另一组配置；不能从两组排序变化单独推断维度或某一个内核的因果作用。

当前 128 维、8,192 的 GPU 时间线仍提供了原生 HugeCTR 慢的直接定位：全 Unique 的 NCCL/其他 kernel 为 **124.43/77.92 ms/步**、重叠 **0**；TorchRec 为 **75.14/75.31 ms/步**、重叠 **22.86 ms/步**。HugeCTR 把表 20 改为 Reduction 后，远端 `send` **487.79→289.98 MB/卡/步**、SendRecv kernel **100.83→62.53 ms/步**、吞吐 **321,611→409,027 samples/s**。当前原生 HugeCTR 的额外耗时主要落在其 embedding 通信路径；它不能代替本 batch 尚未测出的 RAPID 结果。

## GPU 间实际传输路径

本轮单机 8×V100 的物理拓扑同时有 NVLink 和经 PCIe/CPU 互连的 GPU 对。训练配置设 `NCCL_P2P_DISABLE=1`、`NCCL_IB_DISABLE=1`。HugeCTR 的 510 步日志和本次 TorchRec 同配置 1 步传输核查日志中，各有 **128 条 `via SHM/direct/direct` channel**，均无 `via P2P` 或 `via NET` channel。故本轮 NCCL 卡间传输使用**主机共享内存 SHM**，GPU 与主机内存间经过 PCIe；跨 CPU 互连的路径还可能经过主机互连。要排除 NVLink 对本次 NCCL 比较的影响，禁用 P2P 并核验 `via SHM` 已满足，无需物理关闭 NVLink。这不是 GPU 间直接 PCIe P2P；若实验目标特指直接 PCIe P2P，则当前结果不满足该定义。日志里的 `Using network Socket` 是 NCCL 网络后端信息，不能据此说本机卡间数据走 TCP。先前 NVLink payload 计数增量也为零，但该计数不是对全部链路字节的独立测量。
